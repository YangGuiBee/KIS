## 핵심 키포인트
- 구조는 사람(CEO) 아래 AI 에이전트 10명: 9명은 클로드, 1명(전략실장)만 GPT로 구성. CEO는 비서실장 1명하고만 대화하고, 비서실장이 직원 소집·토론·업무배정·검수·승인·보고를 총괄한다.
- 실무 담당자 8명은 역할이 분담됨(콘텐츠·SNS운영·디자인·브랜드/문체·개발·커머스·데이터분석·리서치/컴플라이언스). 담당자뿐 아니라 관련성 낮은 직원도 짧게 의견을 내게 해, 무관해 보이는 한마디가 방향을 바꿀 여지를 남겼다.
- 전략실장(GPT)만 다른 모델을 쓴 이유는 같은 모델끼리 함께 놓칠 부분을 다른 관점에서 보게 하려는 것. 단 승인권은 없고 의견만 내며, 그 의견 수용 여부는 비서실장이 판단(토큰 사용량 절감 목적).
- 토큰 절약 장치: 모든 작업 문서 맨 위에 "이 문서를 보면 무엇을 알 수 있는지"를 한 줄로 적게 해, 전체를 다시 읽지 않고 필요한 문서인지 판단하게 함(성공·실패 기억 장치).
- 개발 환경은 바탕화면에 작업 폴더를 만들고 클로드 데스크톱의 코드 모드와 코덱스(윈도우판)에 같은 폴더를 연결. 계획 세우기 → 실행 순으로 진행한다.
- 지시문 작성법: 처음부터 완벽한 프롬프트를 쓰려 말고 원하는 것과 본인 상황(비개발자·설치된 개발환경 없음 등)을 두서없이 적은 뒤, 일반 채팅에 붙여 "오해 없이 실행 가능하게 개선하고 불명확하면 임의판단 말고 질문하라"고 시켜 다듬는다. 그 후 클로드/코덱스의 계획(Plan) 모드에서 계획을 세우고, 요청 기능이 다 들어갔는지 사람이 확인한 뒤 실행한다.
- Threads 연동이 가장 까다로웠음: 인스타 프로페셔널 계정 전환 → 메타 개발자 등록/앱 생성 → API access 및 threads_content_publish·manage_replies·read_replies 권한 추가 → 콜백/앱시크릿 설정 → Threads 테스터 초대·수락 → 시스템 연결. 테스터 저장 실패 등 시행착오를 캡처해 AI에 보여주며 해결.
- 마지막 교훈: 첫 성과분석 보고서가 형편없이 나옴. 원인은 "좋은 결과물의 기준"(필수 항목·순서·문서 형식·레퍼런스)을 정의하지 않은 것. 또한 API로 글은 올려도 영상은 바로 안 올라가, "브라우저를 직접 조작하는 방식으로 하면 안 되냐"고 되물어 대안을 찾음 — AI가 처음에 방법을 제시하지 않아도 방법이 없는 건 아니라는 점.

## 우리 업무 적용점
- 멀티에이전트를 도입할 때 핵심은 에이전트 수가 아니라 역할 분담·검수 기준·승인 권한·"완료의 정의"를 사람이 명시하는 설계다. KIS/AI팀의 산출물(카드·보고서)도 필수 항목·순서·형식 기준과 레퍼런스를 미리 못 박아야 품질이 안정된다는 점이 우리의 표준·게이트 운영과 맞닿는다.
- 검수·승인 계층(작업자 → 검수자 → 독립 리뷰 → 최종 승인)과 위험도에 따른 최종 승인 주체 분기(고위험=사람, 저위험 반복=자동)는 우리 팀의 리뷰 흐름 설계에 참고할 수 있다.
- 토큰/맥락 절약을 위해 문서 첫 줄에 요약 한 줄을 다는 관례는, 재탐색 시 전체를 다시 읽지 않게 해 비용을 줄이는 실용 팁으로 우리 문서 규칙에 적용해볼 만하다.
- 검수용 리뷰어에 메인과 다른 모델을 두어 관점 다양화를 꾀하는 방식은, 무-지어내기·교차검증을 중시하는 우리 원칙과 통한다(단 승인권과 의견권의 분리로 비용을 통제).
