## ① LLM은 어떻게 "학습"되는가
- **코퍼스→토큰**: 인터넷의 방대한 글(예: ~15조 바이트)을 UTF-8로 숫자화 → 반복 조합을 사전(vocabulary, 대략 15만 규모)으로 압축하는 **토크나이징**. **토큰 ≠ 단어**(단어보다 잘게/다르게 쪼갬, 모델마다 다름).
- **프리트레인(next-token prediction)**: 문장 뒤 토큰을 가리고 "다음 토큰 맞히기"를 무한 반복. 틀리면 **역전파**로 **파라미터(가중치)** 를 조금씩 조정("DJ 테이블" 비유, 수십~수백억 개) → **로스(오차) 최소화**. 결과물 = **베이스 모델**(전력·GPU 비용 수천억대).
- **포스트트레인**: 베이스 모델을 **TPO(상황·형식)에 맞게 사회화** — **파인튜닝/강화학습(RLHF)** 로 가중치 추가·조정. 이 "레시피" 차이가 모델별 벤치마크 특색을 만듦. → 여기까지가 우리가 쓰는 **채팅 모델**.

## ② LLM은 어떻게 "추론"하는가
- 입력 토큰 시퀀스 **임베딩**(벡터화) → **트랜스포머 n개 레이어** 통과.
- 각 레이어: **어텐션**(QKV, 논문 *Attention is All You Need*) 으로 토큰 간 관계·집중도 계산 → **MLP 후가공** → **히든 스테이트**를 다음 레이어로 전달(반복, 어텐션 헤드도 여러 개).
- 마지막: 후보 토큰 점수(**로짓**)를 **소프트맥스**로 정규화 → **샘플링**(temperature·top-k로 후보 추린 뒤 "동전 던지기") → 다음 토큰 확정 → **KV 캐싱**으로 이어감 → 학습된 **stop 토큰**에서 종료.
- 함의: **추론 중 파라미터는 안 바뀜**(고정 모델 사용), 결과는 확률 게임이라 실행마다 달라짐. 컨텍스트가 길수록 어텐션 연산↑·집중력↓(그래서 요약/compaction 발생).

## ③ 핵심 결론 — 프롬프트 vs RAG vs 파인튜닝 언제 쓰나
- **프롬프트/지침(스킬·에이전트 포함)**: **대부분의 일**. 장치 몇 개로 규격이 안정되면 그냥 프롬프트로.
- **RAG**: **근거 기반 답변 + 최신성·업데이트**가 필요할 때. 판단 근거가 크거나 컨텍스트 윈도우를 초과/어텐션이 흐려질 때 → 벡터검색으로 **필요한 것만 찾아 토큰 시퀀스에 주입**. 최신성이 끼면 파인튜닝은 비용상 불가 → **무조건 RAG**.
- **파인튜닝**: **반복적·특화된 태스크 + 대량 반복 + 비용 최적화**일 때만. 예) 하루 100만 번 JSON 규격 응답 → 매번 긴 시스템프롬프트 토큰비용(월 수천만원) → 파인튜닝으로 **맥락/시스템프롬프트를 확 줄여** 자체 운영이 더 쌈. 단, 베이스 모델이 좋아져 **쓸 일이 점점 드묾**(도메인 특화·규모 있을 때).
- 모델 선택: 망분리/로컬 vs 클라우드, 고객 **거버넌스·컴플라이언스** 제약 → 그 안에서 **비용 최적화**가 좌우(모델은 고정 아님, LLM Ops).

## 우리 업무 적용점
- **선택 기준이 곧 실무 판단**: 우리 프로젝트에서도 "이건 프롬프트/스킬로, 이건 RAG(사내규정·최신자료), 파인튜닝은 대량·특화·비용 때만" 원칙 그대로 적용. [[dev-standards-pmo-tool]]
- **확률 게임·컨텍스트 한계 이해** = 무-지어내기·검증 습관의 근거(왜 검증이 필요한지). [[no-fabrication-rule]]
- 컨텍스트 길이·compaction 원리 = 우리가 긴 세션에서 요약/분할하는 이유와 정확히 일치.
